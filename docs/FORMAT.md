# Runbook guide format, version 1

A **runbook** is one file that describes a procedure (set something up, install it, configure it) as an ordered
list of steps. A person reads it in RunbookWizard, which can run the script steps with one click and says what
happened and why. The format is designed so that a **person can write it by hand** and an **AI can generate it
reliably**, and so that a program can **validate it before anything runs**.

- Normative schema: [`schema/runbook.schema.json`](../schema/runbook.schema.json) (JSON Schema 2020-12).
- Decision record: [ADR 0003](decisions/0003-guide-format.md), execution and trust: [ADR 0004](decisions/0004-execution-model-and-trust.md).
- Examples (validated by the test suite): [`docs/examples/`](examples/).

## 1. Two serializations, one model

| File | Form | Use |
|---|---|---|
| `name.runbook.md` | Markdown with YAML frontmatter (preferred) | writing by hand, generating with an AI |
| `name.runbook.json` | JSON | machine interchange, generated by tools |

Both describe the same **canonical model** (section 6). The Markdown form is converted to that model, which is then
validated against the schema and checked semantically (section 7). Loading a guide never executes anything.

## 2. Markdown form

````markdown
---
runbook: 1
title: Install and configure the thing
description: One or two sentences (optional).
shell: powershell
variables:
  - name: SiteName
    label: Site name
    default: demo
---

Optional introduction (Markdown). Used as `description` when the frontmatter has none.

## Step title

```step
type: script
destructive: false
```

What this step does, in plain Markdown. Can be several paragraphs and lists.

### Why

Why the step exists and what goes wrong without it.

```powershell
Get-Service W3SVC
```
````

Rules, in full:

1. The file starts with a YAML **frontmatter** block between `---` lines. It must contain `runbook: 1` and `title`
   (or the body has a `# ` heading which is then the title). All other canonical top-level fields are allowed there
   (`description`, `version`, `author`, `tags`, `platforms`, `shell`, `variables`). `steps` is **not** written in the
   frontmatter; it is built from the body.
2. In the body, every **level-2 heading** (`## `) outside a code fence starts a step; its text is the step `title`.
   Text before the first `## ` (and a single `# ` title line) is the guide introduction.
3. Inside a step section:
   - the first fenced block whose info string is `step` contains the **step attributes** as YAML (section 3). It
     is optional; without it the type is inferred (a script block makes it `script`, otherwise `info`).
   - the first fenced block whose info string is a shell name (`powershell`, `pwsh`, `winps`, `bash`, `sh`, `cmd`)
     is the **script**. The info string also sets the step `shell` (`powershell` is the guide default).
     A second shell block in one step is an error; show example code in a block tagged otherwise (`text`, `json`, ...).
   - a level-3 heading `### Why` starts the **why** text, which ends at the next level-3 or higher heading.
   - everything else is the **description** (Markdown, kept as written).
   **Runme-style shorthand:** attributes may follow the shell tag on the opening fence, in Runme's notations:
   ```` ```powershell { name=install destructive=true timeoutSeconds=90 } ```` or ```` ```bash {"name":"install"} ````.
   `name` is the step `id`; any other step field works. Attributes in a `step` block win over these. Use the block
   for anything longer than a few scalars (`success`, `captures`, `env`). Values containing `{{` must be quoted
   (in YAML too: `when: "{{os}} == windows"`).
4. The attributes in the `step` block must not repeat `title`, `description`, `why` or `script`; those come from the
   Markdown structure. They may set everything else.
5. Code fences are ```` ``` ```` or `~~~`; a heading inside a fence is not a heading.

The step id is `id` from the attributes or the slug of the title (`Create the site` -> `create-the-site`; a repeated
slug gets `-2`, `-3`).

## 3. Step attributes

| Field | Type | Default | Meaning |
|---|---|---|---|
| `id` | string `[a-z0-9-]` | slug of title | Stable identifier (used by `when`, logs, references). |
| `title` | string | (heading) | Short imperative name. |
| `type` | `info` / `manual` / `script` / `choice` | inferred | `info` is read only; `manual` the person does something and confirms; `script` has a Run button; `choice` asks the person to pick a way (section 5.1). |
| `description` | Markdown | | What to do. |
| `why` | Markdown | | Why it is needed; what an error here usually means. |
| `confirm` | string | "Done" | `manual` only: the sentence the person confirms ("I have restarted the machine"). A manual step may hold a checklist, see section 5.3. |
| `shell` | `powershell` `pwsh` `winps` `bash` `sh` `cmd` | guide `shell`, else `powershell` | See section 5. |
| `script` | string | | The script body (a `script` step must have one; `info`/`manual` must not). |
| `workingDirectory` | string | the guide's folder | Supports `{{Variable}}`. |
| `timeoutSeconds` | int 1-86400 | 600 | The step is killed after this long. |
| `env` | map string->string | | Extra environment variables; values support `{{Variable}}`. |
| `destructive` | bool | false | Deletes or overwrites data / changes the system irreversibly. Needs an extra confirmation. |
| `warning` | string | | Shown prominently above the Run button. |
| `elevated` | bool | false | Says the step needs administrator/root rights. The player does not elevate for you. |
| `when` | condition | | Offered only when true, otherwise skipped (section 4.3). |
| `success` | object | exit code 0 | `exitCodes: [0, 3010]`, `outputMatches: regex`, `outputNotMatches: regex`. All given rules must hold. |
| `captures` | list | | After a run, `{ variable: Name, pattern: regex }` stores output text into a variable for later steps. |
| `continueOnFailure` | bool | false | A failed step does not block the steps after it. |
| `next` | step id | the following step | Jump target after the step succeeded or was skipped (section 5.1). Ignored (warning) on a `choice`. |
| `onFailure` | step id | | Jump target when the step failed; the steps in between are skipped (section 5.1). |
| `options` | list | | `choice` only, at least two: `{ label, goto, description? }`; `goto` is the id of the step that follows. |

## 4. Variables, substitution, conditions

### 4.1 Variables (frontmatter `variables`)

| Field | Meaning |
|---|---|
| `name` | Identifier `[A-Za-z_][A-Za-z0-9_]*`. |
| `label`, `description` | Shown next to the input. |
| `type` | `string` (default), `number`, `bool`, `choice` (needs `choices`), `path`, `secret`. |
| `default` | Initial value. |
| `required` | The person must fill it before any step that uses it can run. |
| `pattern` | Regular expression the **whole** value must match. |

The person enters values once, on the Parameters page; they are kept in memory for the session. `secret` values
are masked in the UI, in the command preview and in logs and are never saved.

### 4.2 Substitution

`{{Name}}` in `script`, `workingDirectory` and `env` values is replaced by the variable's value **as plain text, with no
quoting or escaping** - validate with `pattern` or write the quotes yourself (`'{{SiteName}}'` in PowerShell).
`\{{Name}}` stays literal `{{Name}}`. Every variable (also secrets) is additionally available to the process as the
environment variable `RUNBOOK_VAR_<Name>` (PowerShell: `$env:RUNBOOK_VAR_SiteName`); **prefer that for secrets** so the
value is never part of the script text.

Built-in values: `{{os}}` (`windows`, `linux`, `macos`), `{{runbookDir}}` (the folder of the guide), `{{user}}`.
A step that `captures` a variable defines it for later steps. A `{{Name}}` that no variable, capture or built-in
defines is a validation error.

### 4.3 Conditions (`when`)

```
expr     := or
or       := and ( '||' and )*
and      := not ( '&&' not )*
not      := '!' not | '(' expr ')' | compare
compare  := operand ( ('==' | '!=') operand )?
operand  := {{Name}} | 'text' | "text" | bareword
```

Comparison is case-insensitive. A lone operand is true when it is not empty and not `false`, `0` or `no`.
Examples: `{{os}} == windows`, `{{Mode}} == 'prod' && {{Backup}}`, `!{{SkipTls}}`.

## 5. Execution semantics

- A script step runs **only on a click**, after the exact text (parameters substituted) was shown (ADR 0004).
- `powershell` means PowerShell 7 (`pwsh`) when installed, else Windows PowerShell; `pwsh` and `winps` (Windows
  PowerShell 5.1) pin one of them; `bash` / `sh` / `cmd` as named (`cmd` is `cmd.exe /d /q /c`).
- The script is written to a temporary UTF-8 file. PowerShell steps run in a wrapper that sets
  `$ErrorActionPreference = 'Stop'` before your script (set it back inside the script if you want the old behaviour)
  and then exits with the exit code of the last native command. Other shells run the file unchanged - start `bash`
  scripts with `set -euo pipefail`.
- Output (stdout and stderr) is streamed live and kept for the success rules and `captures`.
- All regular expressions are .NET regular expressions evaluated with `Multiline` (`^`/`$` match at every line) and
  are not subject to `{{...}}` substitution.
- Success: exit code in `success.exitCodes` (default `[0]`), `outputMatches` found, `outputNotMatches` absent.
  The player reports which rule decided.
- Statuses: pending, running, done, failed, skipped. A failed step offers Retry and Skip; later steps stay available
  only if `continueOnFailure` is set, the step has an `onFailure` route or the person skips the failed one.

### 5.1 Branching

Without `next`, `onFailure` and `choice` a guide is a straight line, exactly as before. Branching is derived, never
stored: the path through the guide is computed from the statuses of the steps.

- A step that is done or skipped continues at its `next`, else at the following step.
- A `choice` step is done when the person picked an option; the guide continues at that option's `goto`. Picking another
  option later (or Reset) re-routes the path.
- A failed step continues at its `onFailure`; without it, with `continueOnFailure` at `next`/the following step; otherwise
  it blocks (Retry or Skip).
- A step that cannot be reached any more on the current path is shown as skipped ("skipped by branch"). It is reversible:
  when the path changes it is offered again. A step skipped by `when` stays skipped by its condition.
- Targets are step ids. Jumps may go forward or back, but a path that leads back to a step it already visited (a loop) is a
  validation error; retry covers repeating a step. `next`/`onFailure`/`goto` naming an unknown id is a validation error.
- Captured values are checked in file order: a step may only use a capture defined by an earlier step in the file.
- `when` keeps working and combines with branching: a step whose condition is false is skipped and the path continues
  at its `next`.

### 5.2 Parameters in the command

The command preview shows every `{{Name}}` of a declared variable as an editable field inside the highlighted command;
the rest of the command is read only. It edits the same value as the Parameters page. Type, default, choices, `pattern`
and the secret flag come from the variable declaration (a secret is entered masked and stays masked). Nothing about the
format changes: authors write `{{Name}}` as before. `\{{Name}}` is shown literally.

### 5.3 Checklists in manual steps

A `manual` step can list several things to do. Write them as Markdown task-list lines in the step text:

````markdown
## Prepare the workstation

```step
type: manual
confirm: The workstation is ready
```

Go through the machine:

- [ ] Sign out of every personal account
- [ ] Update Windows and **restart** once
- [ ] (optional) Wipe the browser profile
````

- An item is a line `- [ ] text` (`*` and `+` bullets work too, no indentation beyond 3 spaces, one line per item). `- [x]` is not an item.
  Lines inside a code fence are examples and are left alone.
- An item that starts with `(optional)` (any case) may stay unticked; every other item is **required**.
- The player shows the items as checkboxes under the step text (the rest of the text is rendered as Markdown as usual) and keeps the
  confirm button disabled until every required item is ticked. Reset clears the boxes. Item text is plain text: `code`, `**bold**` and
  links lose their markers.
- It is only part of the text, so the JSON form needs nothing new: put the same lines in `description`. The schema is unchanged.
- A checklist in a step that is not `manual` is shown as plain text (warning). Ticks are kept for the run only for now (ADR 0010).

## 6. Canonical model (JSON)

```json
{
  "runbook": 1,
  "title": "Install and configure the thing",
  "shell": "powershell",
  "variables": [{ "name": "SiteName", "default": "demo" }],
  "steps": [
    {
      "id": "check-service",
      "title": "Check the service",
      "type": "script",
      "description": "Looks whether the web server service exists.",
      "why": "Everything after this assumes it is installed.",
      "script": "Get-Service W3SVC",
      "success": { "exitCodes": [0] }
    }
  ]
}
```

This is exactly what `*.runbook.json` contains. The schema is the single normative definition of the fields.

## 7. Validation

Two layers; the player shows the findings with their path (`steps[3].success.outputMatches`) before the guide opens.

1. **Schema** (structure, types, enums, required fields).
2. **Semantic checks** (errors unless marked warning): duplicate step ids; `{{Name}}` that is undefined; a variable
   used before a step captured it; invalid regular expression in `pattern`, `success`, `captures`; malformed `when`;
   `when` referring to an unknown variable; `next`, `onFailure` or an option `goto` naming an unknown step; a loop; a
   `choice` with fewer than two options or a duplicate option label; `options` on a step that is not a `choice`; `choice` default not among the choices; an unknown field anywhere (also
   in the frontmatter, never silently ignored); a script step without script.
   Warnings: a checklist in a step that is not manual, a manual checklist whose items are all optional; a script the risk scanner finds potentially destructive but that is not marked `destructive`; a
   `destructive` step without a `warning`.

A guide with errors can be inspected but not run.

## 8. Quick reference for AI authors

Write a `.runbook.md` file. Checklist:

1. Frontmatter with `runbook: 1`, `title`, `description`, `platforms`, and `variables` for everything the reader must choose
   (never hard-code paths, names, secrets).
2. One `## ` section per step, in execution order, small steps (one command or one decision each).
3. Every step explains **why** (`### Why`), including what an error usually means.
4. Prefer a check step before and after every change (`success.outputMatches` or exit code) so the player can tell
   whether it worked.
5. Mark anything that deletes, overwrites, reinstalls, reboots or changes security as `destructive: true` with a `warning`.
6. Use `type: manual` for things a script cannot do (sign in to a portal, reboot, approve a prompt); several things in one go are a `- [ ] item` checklist (section 5.3, `(optional)` for the ones that need not block).
7. Scripts must be non-interactive, idempotent where possible, and print what they did.
8. Secrets are `type: secret` variables read from `$env:RUNBOOK_VAR_<Name>`, never `{{Name}}` in the script text.
9. Use `type: choice` for a real decision, `onFailure` for a recovery step, and `next` on the last step of each path. See `examples/branching-deploy.runbook.md`.
10. Use exact commands, not "something like"; if it depends on the OS or a variable use `when`.
10. Never include commands to download-and-execute unknown code (`iwr ... | iex`); the reader sees every command first.

Minimal template:

````markdown
---
runbook: 1
title: <what this achieves>
description: <one sentence>
platforms: [windows]
variables:
  - { name: Target, label: Target folder, type: path, default: 'C:\Tools', required: true }
---

## Check prerequisites

Checks that the folder is writable.

### Why

The install step fails with "access denied" if it is not.

```powershell
Test-Path '{{Target}}'
```

## Install

```step
destructive: true
warning: Overwrites an existing installation.
success: { outputMatches: 'Installed' }
```

Copies the files.

```powershell
Write-Output 'Installed'
```
````
